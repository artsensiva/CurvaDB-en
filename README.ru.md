# CurvaDB

English version: [README.md](README.md)

Проект теперь состоит из двух частей. Первая (`step0`-`step3`) — завершённое
исследование: даёт ли хранение GPS-траекторий кубическими B-сплайнами
выигрыш над классической схемой "упрощение Дугласом-Пекером (DP) +
поиск по дискретной метрике Фреше"? Итог — отрицательный результат по
сжатию для потребительского GPS; для точных данных выигрыш в
проверенных условиях тоже не найден, но вопрос до конца не закрыт (см.
гипотезу H1 в [docs/ru/findings.md](docs/ru/findings.md)). Это исследование
завершается — следующий шаг для него не код, а интервью с отраслью (см.
[docs/ru/next_steps.md](docs/ru/next_steps.md)).

Вторая часть, **step7**, — положительный результат: сертифицированное хранилище
кривых, отвечающее на диапазонные запросы по сжатым траекториям с доказанной
гарантией на истинную непрерывную метрику Фреше, дешевле чтения исходных данных.
Ворота G1 (`docs/ROADMAP.md`) открыты — см. раздел
[Сертифицированное хранилище кривых (step7)](#сертифицированное-хранилище-кривых-step7) ниже.

## Этапы

| Этап/шаг | Вопрос | Ответ |
|---|---|---|
| A. Исходная идея | Семантический поиск через "кривые" над эмбеддингами? | Реализовано (Level 1-2), но не доведено до сравнения с baseline. |
| B. Критика | Состоятельна ли идея математически? | Нет — 4 несвязанные задачи, порядок координат эмбеддинга произволен. Пивот на GPS-траектории. |
| C. Проверка фактов | Пуста ли ниша, честно ли сравнение? | Ниша не пуста; сравнение "80КБ/2-4КБ" нечестное; рекомендованы 10-15 интервью — не проведены. |
| D. Организация | — | Ветка `trajectory-pivot`, данные GeoLife, промпты файлами. |
| step0 | Как наивный сплайн смотрится против DP? | Разгромно хуже (recall 0.707 против 0.997) — оказалась методическая ошибка (`docs/ru/results/step0_diagnostics.md`). |
| step1 | Что покажет честная методика? | Recall почти сравнялся (0.972/0.996), но сжатие DP выигрывает на каждом tol (3.7x при tol = 10 м). |
| step2 | Есть ли ниша сжатия по шуму/tol? | Узкая зона нашлась (tol=1-5м, sigma<=0.1м) — но только для RTK/лидарной точности. |
| step3 | Выдержит ли гипотеза решающую проверку без привязки к ломаной? | Все три критерия (K1-K3) провалены; даже оракул (с равномерными узлами) не компактнее DP+SED. **Вывод step2 о нише отменён.** |
| Резолюция | Что дальше? | Не код — 8-10 интервью с отраслью; порог возврата к коду ≥3/10. |

Полная хронология с цифрами и коммитами — [docs/ru/history.md](docs/ru/history.md).

## Сертифицированное хранилище кривых (step7)

Второй исследовательский вопрос, дальше по тому же репозиторию: может ли хранилище кривых
отвечать на диапазонные запросы по *сжатым* траекториям с доказанной гарантией на истинную
непрерывную метрику Фреше, вместо чтения исходных данных для каждого кандидата? Ответ — да,
с реальными, измеренными компромиссами. Ворота G1 (`docs/ROADMAP.md`) открыты.

- Точный поиск с гарантией по сжатым данным: **0 пропусков и 0 лишних ответов на 6 000 000**
  комбинаций (запрос, кандидат, диапазон, представление).
- Сертифицированный метод **вдвое быстрее точного фильтра без сжатия** (20.1 мс против 41.7 мс
  медианного времени на запрос) — при этом он медленнее *несертифицированного* приближённого
  поиска по тем же сжатым данным — отдельный, задокументированный компромисс (S6b).
- Цена отказа от гарантии, измеренная явно: приближённый поиск без сертификатов по тем же сжатым
  данным всё равно даёт **0.03-3.03%** пропусков истинных ответов.
- Компромисс допуск/объём для представления-ломаной: ужесточение упрощения до уровня, решающего
  запросы на коротком радиусе без чтения исходных данных, стоит реального роста объёма
  в **5.1 раза** на трек.
- Отрицательный результат внутри положительного: собственный *основной* сертификат сплайна из
  спецификации (раздел 2.3) доступен только для **16.4%** реальных треков и там, где доступен,
  в **1.68 раза** грубее собственного документированного резервного пути (раздел 2.4) — решено
  тем, что этот резервный путь сделан основным по умолчанию
  (`docs/decisions/ADR-0018-2-4-primary-spline-certificate.md`).

## Установка

```bash
python3 -m venv venv
venv/bin/pip install -r requirements-research.txt
```

(`requirements.txt` относится к старому проекту Level 1/2, `src/level1`;
исследование траекторий использует `requirements-research.txt`.)

Данные — GeoLife Trajectories 1.3 (`data/geolife/<user_id>/Trajectory/*.plt`),
в репозиторий не входят (см. `.gitignore`).

## Как воспроизвести

```bash
venv/bin/pytest tests/traj/                          # тесты

venv/bin/python benchmarks/step0.py                  # первый (сломанный) замер
venv/bin/python benchmarks/step1_clean.py             # чистка данных
venv/bin/python benchmarks/step1_spline_fit.py         # честный густой фиттинг
venv/bin/python benchmarks/step1_compression.py        # сжатие (гипотеза A)
venv/bin/python benchmarks/step1_kinematics.py         # кинематика (гипотеза B)
venv/bin/python benchmarks/step1_search.py             # recall@10
venv/bin/python benchmarks/step2_crossover.py --pilot  # поиск ниши (пилот)
venv/bin/python benchmarks/step2_crossover.py          # поиск ниши (полный прогон)
venv/bin/python benchmarks/step3_decisive.py --pilot   # решающий эксперимент (пилот)
venv/bin/python benchmarks/step3_decisive.py           # решающий эксперимент (полный прогон)

# step7 -- сертифицированное хранилище кривых (docs/specs/step7_B_certified_store.md)
venv/bin/python benchmarks/step7_certify.py            # M0-M1: сертификаты ломаных + сплайнов (раздел 2.4)
venv/bin/python benchmarks/step7_m13_fitters.py        # M1.3: сравнение фиттеров (fit_adaptive против spline.fit())
venv/bin/python benchmarks/step7_m13_tail.py           # M1.3: проверка хвоста eps_A/LB
venv/bin/python benchmarks/step7_m2_projection.py      # M2: основной сертификат сплайна (раздел 2.3), полный корпус
venv/bin/python benchmarks/step7_query.py              # M3: интервальные запросы, полный корпус + почти-дубликаты
venv/bin/python benchmarks/step7_m4.py                 # M4: доля ошибок, компромисс tol/объём, задержка на запрос
```

Каждый скрипт пишет свою секцию в `benchmarks/results/<step>.md`
(в этом репозитории отчёты на английском; русские копии — в
docs/ru/results/, скриптами не обновляются).

## Известные альтернативы

- **PostGIS** ([`ST_FrechetDistance`](https://postgis.net/docs/ST_FrechetDistance.html)) —
  дискретная метрика Фреше как встроенная функция SQL над `geometry`;
  готовое индустриальное решение без необходимости писать свою ДП.
- **[MobilityDB](https://mobilitydb.com/)** — расширение PostgreSQL/PostGIS
  для траекторных данных (`tgeompoint` и т.п.), с временными операциями,
  индексами и метриками схожести из коробки.
- **Map-matching** (например, [Valhalla](https://github.com/valhalla/valhalla),
  [OSRM](https://project-osrm.org/)) — привязка GPS-трека к дорожной сети;
  другой подход к сжатию/представлению траектории, снимающий часть шума
  за счёт внешней информации о графе дорог, а не только геометрии трека.
- **Сглаживание Калманом** (constant-acceleration + RTS) — в step1
  (`docs/ru/findings.md`, `docs/ru/results/step1.md` §4) показал лучшую
  среднюю точность восстановления скорости/ускорения среди всех трёх
  сравненных методов, ценой заметно более низкого recall детекции
  резких манёвров — альтернатива для задач, где важна кинематика, а не
  геометрическое сжатие/поиск.
