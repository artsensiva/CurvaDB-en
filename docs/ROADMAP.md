# ROADMAP: исследования и продукты на основе кривых и поверхностей

Документ задаёт порядок работ, ворота между фазами и правила принятия решений для шести
спецификаций в `docs/specs/`. Разделы «Ворота» и «Правила» меняются только отдельным коммитом
с обоснованием в журнале решений (раздел 8), не во время выполнения фазы.

## 1. Спецификации

| Код | Файл | Тип | Кратко |
|---|---|---|---|
| step7 (B) | `docs/specs/step7_B_certified_store.md` | исследование | Сертификаты Фреше для любых представлений, интервальные запросы |

## 2. Зависимости

```
step7 ──► step8
  │
  ├──► ядро certigeo (кривые) ──► P3
  │                          ├──► P1
  │                          └──► P4 (только производные сплайнов)
  │
  └──► ядро certigeo (поверхности) ──► P2
```

- step7 создаёт кривую часть ядра: непрерывная метрика Фреше, вставка узлов, выделение Безье,
  сертификаты через выпуклую оболочку.
- step8 использует сертификаты step7.
- P3 — step7, доведённый до продукта на ломаных.
- P1 использует сертификат «капсула плюс монотонная проекция» из step7.
- P2 требует поверхностной части ядра и OpenCASCADE.
- P4 почти независим.

## 4. Ворота

### G0. Старт

- [x] Все шесть спецификаций и обзор закоммичены в `docs/specs/`.
- [x] Разделы «Приёмка» в спецификациях закоммичены отдельным коммитом (хэш записан в раздел 8).
- [x] Разосланы первые запросы на интервью во всех трёх доменах (раздел 6).

### G1. Сертификаты работают (после step7)

Обязательно все:

- [ ] S1 и S2: корректность сертификатов ломаных и сплайнов — 100%.
- [ ] S3: медиана `ε/LB` ≤ 1.2 для ломаных и ≤ 2 для сплайнов.
- [ ] S4: 0 пропусков и 0 лишних в запросах.

Исходы:

- **Всё выполнено** → фазы 2 и 3.
- **S3 для сплайнов хуже 5** → сплайны исключаются из хранилища; фаза 2 выполняется в
  сокращённом виде (только ломаные и оракул); P1 пересматривается (раздел 7, риск R1).
- **S1, S2 или S4 не выполнены** → ошибка реализации; фаза 1 не закрывается до исправления.

### G2. Вывод по H1 (после step8)

- [ ] В `benchmarks/results/step8.md` записан вывод по H1 по правилу из раздела 8 спецификации.
- [ ] A4, A5, A6 выполнены (иначе вывод недействителен).

G2 не блокирует продуктовые фазы.

### G3. Ядро готово

- [ ] Пакет `certigeo` (кривые) выделен из кода step7, код step7 использует пакет.
- [ ] Тесты свойств ядра проходят на 10 000 случайных кривых; покрытие строк ≥ 90%.
- [ ] Вставка узлов не меняет кривую (≤ 1e-12 · L); совпадение с `scipy.interpolate.BSpline`
      до 1e-12.

### G4. Выбор первого и второго продукта (P1, P2)

Порог спроса для домена: **не менее 3 из 10** собеседников независимо называют проблему, которую
решает продукт (формулировки проблем — раздел 6).

| Результат интервью | Фаза 4 | Фаза 5 |
|---|---|---|
| P1 и P2 прошли | P1 | P2 |
| Только P1 | P1 | — (фаза 6 поднимается) |
| Только P2 | P2 | — (фаза 6 поднимается) |
| Ни один | — | — |

Почему при двух прошедших первым идёт P1: он переиспользует кривые сертификаты напрямую, не
требует OpenCASCADE, его ценность проверяется в симуляции. Перед P2 выполняется поверхностная
часть ядра (входит в оценку фазы).

Если ни один не прошёл, продуктовые фазы 4–5 не начинаются; публикуются результаты step7 и step8.

### G5. Внутри продуктовой фазы

Если G6 открыты раньше, чем завершены интервью для P1/P2, P3 может выполняться сразу после фазы 3.

## 5. Цикл работы внутри фазы

1. Промпт этапа (`docs/prompts/<код>_M<n>.md`) ссылается на спецификацию и называет только пункты
   этапа.
2. Агент показывает план, получает «ок», работает с коммитом после каждого пункта.
3. Отчёт этапа с таблицей «критерий / порог / факт / выполнен».
4. **Ревью постановки** (`docs/reviews/<код>_M<n>.md`), чек-лист:
   - [ ] метрика и соперник совпадают со спецификацией;
   - [ ] нет совпадающих чисел у методов, которые должны различаться;
   - [ ] прошлое исправление не стало ограничением;
   - [ ] гарантия проверена там, где используется;
   - [ ] разделы «Приёмка» не изменены (`git diff <хэш G0> -- docs/specs/`).
5. Решение: следующий этап, доработка или остановка.

Шаблон промпта:

```
Выполни этап M<n> из docs/specs/<файл>.md. Контекст — CLAUDE.md и docs/ROADMAP.md.
Раздел «Приёмка» не менять. Новые зависимости — только из раздела «Стек».
Коммит после каждого пункта, незавершённое — в TODO.md.
В конце — отчёт с таблицей «критерий / порог / факт / выполнен».
Уточняющих вопросов не задавать, если ответ есть в спецификации.
Сначала короткий план, жди «ок».
```

## 6. Интервью

Идут параллельно с фазы 0. Протоколы — `docs/interviews/<домен>/<дата>_<роль>.md`
(без персональных данных без согласия).

| Домен | Для | С кем | Проблема, которую нужно услышать (засчитывается в порог) |
|---|---|---|---|
| Высокоточная обработка | P1 | технологи-программисты ЧПУ, инженеры пресс-форм, аэрокосмос, импланты | потеря времени или качества поверхности из-за сегментированных траекторий и снижения подачи; потребность в подтверждённой точности пути |
| Контроль качества | P2 | инженеры ОТК, метрологи, аддитивное производство, литьё | ложные или спорные решения «годен/брак» у границы допуска; недоверие к расчёту по сетке; трудоёмкость документирования неопределённости |
| Робототехника и беспилотники | P3, P4 | инженеры по данным и валидации, исследователи обучения по демонстрациям | пропуски похожих случаев при поиске в логах (P3); поиск движений по форме независимо от положения (P4) |

Правила подсчёта:

- Засчитывается, только если собеседник назвал проблему **сам**, до описания продукта.
- Один собеседник засчитывается в одном домене один раз.
- Порог 3 из 10 проверяется после 10 интервью в домене; раньше — только если 3 уже набраны.

Базовые вопросы (без упоминания продукта):

1. Опишите последний случай, когда геометрия или траектория стоила вам времени или денег.
2. Как вы сейчас это решаете и что в этом неудобно?
3. Что происходит, если результат расчёта или поиска ошибочен?
4. Сколько это стоит (время станка, брак, часы инженера, риск)?
5. Пробовали ли вы готовые решения, почему они не подошли?
