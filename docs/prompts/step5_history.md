## Факты до step0 (из обсуждения вне репозитория)

Этап A. Исходная идея CurvaDB (см. docs/legacy.md): семантический поиск,
документы как "кривые"; Hilbert-индекс над эмбеддингами sentence-transformers
(Level 1), сплайны и функциональный PCA (Level 2), метрики Фреше/DTW, план
Level 1-3.

Этап B. Критика идеи (внешние заметки + анализ):
- четыре несвязанные математические задачи (кривая Гильберта — индекс;
  сплайн — представление; fPCA — редукция; Фреше/DTW — метрика), объединённые
  только словом "кривая";
- порядок координат эмбеддинга произволен, поэтому "кривая через 768 координат"
  не несёт смысла: ни сжатия, ни осмысленных производных;
- совет: один тип кривой, один домен, где параметр t физически осмыслен
  (время), одна метрика, сначала линейный baseline;
- предложено: хранилище GPS-траекторий на кубических B-сплайнах с поиском
  по Фреше; веха 1 — телематика автопарков (потребительский GPS), веха 2 —
  траектории в R3 (медицинская робототехника, роботы).

Этап C. Проверка фактов перед стартом:
- ниша не пуста: PostGIS имеет ST_FrechetDistance, есть MobilityDB, в
  телематике распространён map-matching;
- сравнение "80 КБ ломаная против 2-4 КБ сплайн" было нечестным: честный
  соперник — ломаная после Дугласа-Пекера;
- рекомендовано: сначала бенчмарк против реальных соперников и 10-15
  интервью с отраслью. Интервью НЕ проводились за весь проект.
- решение по стеку: Python (scipy, shapely, numba) для исследования; Rust
  (PyO3, pgrx) имеет смысл только для будущего продукта.

Этап D. Организация работы: ветка trajectory-pivot, данные GeoLife 1.3,
Claude Code в VS Code, контекст в CLAUDE.md. Уроки процесса: промпты хранить
файлами в docs/prompts/ (переживают перезапуски, экономят лимит); не
перезапускать VS Code во время фоновых прогонов; длинные прогоны — пилот с
лимитом времени перед полным.

## Факты анализа по шагам (дополнять цифрами из results/*.md)

step0: помимо цифр — байты сравнивались без меток времени у DP; recall
сплайна 0.707 оказался следствием колебаний сплайна между метками
(step0_diagnostics.md: 82% треков, медиана около 110 м).

step1: внешние замечания к результатам:
- для сплайна честный соперник по сжатию — DP+SED (оба учитывают время),
  а не обычный DP; разрыв сокращался с уменьшением tol;
- кинематика ненадёжна как тест: tol=10 м при шуме 5 м, всего 74 точки с
  |a|>3 м/с2, Калман настроен по RMSE ускорения (отсюда низкий recall);
- в реальной телематике манёвры детектируют акселерометром, скорость берут
  из доплеровских измерений GNSS, а не дифференцируют координаты.

step2: главная находка анализа — сплайн был привязан к ломаной (контракт
fit() держит tol до прямых отрезков между отсчётами): доли достижимых треков
у сплайна и DP совпали во всех клетках (3/30, 25/30, 24/30, 26/30); ошибка
хорды L^2/(8R) объясняет недостижимость малых tol даже при sigma=0. Внешний
комментарий после step2 предлагал нишу RTK/лидар, отказ от продажи "сжатия"
и поиск по профилю кривизны kappa(t).

step3: критерии K1-K3 зафиксированы ДО запуска (docs/prompts/step3.md).
Ограничения, выявленные после: при dt=15 с поворот целиком внутри интервала —
предел информации для любого метода; sigma=5 при tol=10 слишком жёстко для
max-нормы; DP+SED — слабый соперник для реконструкции (честные: Калман,
эрмитова интерполяция с доплеровской скоростью); LSQ-фиттер без регуляризации.

## ОБЯЗАТЕЛЬНОЕ исправление выводов

Сначала проверь в src/traj/spline_lsq.py, какие узлы использует fit_oracle.
Если только равномерные: оракул — потолок для РАВНОМЕРНЫХ узлов, а не
теоретический предел сплайна. В step2 (step2.md §3) адаптивные узлы FITPACK
дали около 0.70x контрольных точек против равномерных, поэтому оптимальная
расстановка узлов могла бы приблизить K1. Во всех документах заменить
"устойчиво вплоть до теоретического предела", "сама репрезентация не даёт
выигрыша" и подобное на: "в проверенных условиях (равномерные узлы у оракула)
выигрыша по сжатию нет; оптимальная расстановка узлов не проверена". Отметить,
что на практическое решение это не влияет: экономия порядка 30% байт не
является продуктовой ценностью.

Открытых гипотез ДВЕ, разделить явно:
H1 (сжатие): свободные/оптимальные узлы на точных данных — не проверено.
H2 (продукт): аналитические производные и поиск по профилю кривизны kappa(t)
на точных данных (RTK, роботы, дроны) — не проверено, спрос не подтверждён.

## Резолюция (зафиксировать дословно по смыслу)

- Сплайн как компрессор траекторий потребительского GPS — закрыто (step1, step3).
- Сжатие на точных данных — выигрыша в проверенных условиях нет, H1 открыта,
  но не приоритетна.
- Следующий шаг — не код, а 8-10 интервью (робототехника, агротехника с RTK,
  дроны, хирургическая робототехника). Вопросы: как храните и сравниваете
  траектории; нужен ли поиск похожих движений; откуда берёте скорость и
  кривизну — из сенсоров или вычисляете по координатам; что сейчас неудобно.
- Порог возврата к коду: не менее 3 из 10 собеседников независимо называют
  задачу поиска/сравнения траекторий по форме или кинематике, которую текущие
  инструменты не решают. Тогда — эксперимент по H2 на KITTI или TUM RGB-D с
  критериями, зафиксированными до запуска. Иначе проект завершается как
  исследование с опубликованным результатом.
